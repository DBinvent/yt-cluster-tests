51 findings, every one fixed - none critical, from the first run on

From the first run on build 1.20.1, none of the first 30 findings was a crash or left the cluster going on from a divergent state, the two outcomes that would matter most: in the logs kept, every ytserv exit was the test's own kill or stop, and under all a row whose copies differed took no further write until it was repaired, so every failure stayed inside single rows, availability, or one node left behind.

That containment is the architecture YT Cluster was started on six years ago, and the first Jepsen runs prove it.

The retests that followed found rarer ones, and the nightly two more: two stopped a node from starting after a kill at the wrong moment, a WAL file or page half written (43, 45), and one gave a term two leaders (42). Every one is fixed, and the last build passed every run of the retest matrix.

Most of the fixes improve usability: they remove the need for workaround solutions, to meet the expectation of a high level of user-friendly experience.

Divergence under half, which takes no vote from the nodes outside a commit's party, is a misconfiguration: a guardrail can refuse it, and the code now blocks such a row (fix 29). half is available but nobody runs it, and the fix is in YT Cluster 1.20.

Jepsen is the industry standard for testing data consistency in a cluster, designed to compromise data integrity on purpose: its synthetic faults (partitions, killed and paused processes, damaged packets) force in minutes the very rare cases a production cluster is very unlikely to meet. It is very picky and very aggressive, and Elle checks every transaction the clients saw. Serious databases publish their results, in the independent Jepsen analyses (PostgreSQL, MySQL, etcd, MongoDB, CockroachDB, YugabyteDB, TiDB) and on their own sites: MongoDB, Cockroach Labs (and nightly), YugabyteDB. These runs use the open-source Jepsen framework; they are not an analysis by Jepsen.

Five nodes, jepsen-io/sql's append and rw workloads judged by Elle, with partitions, killed and paused ytserv, and packet faults. On build 1.20.1 every run was invalid. The night matrix covered 26 cases (sequential, strong, and half for node bouncing, each also with recon): 35 of 37 runs passed on the night's last build, against 21 failed runs of 122 before its fixes. The retests ran the matrix again on seven builds with fixes, 2026-10-23 to 25: 397 runs, 15 of them failed, each a finding fixed before the next build - and the last build passed all 49 of its runs. Four of the cases run in the nightly as a suite of their own. The findings in full, with every retest: findings.md; the test: jepsen/ in the public tests repository.

We continue improving and monitoring YT Cluster as new features come, and the Jepsen test project is updated with them.

severe #1 1 of 51

A duplicate insert committed although every member refused it

sequential, append, partition + kill + pause (2026-10-22, build 1.20.1)

What happened
Under all, the four other nodes failed a second insert of the same key with a duplicate-key error. Each was dropped from the party, the origin committed alone, and its trigger returned no error. Both inserts were acknowledged to their clients.
Left behind
Two copies of one key: one node holds a value no other has.
Self-repair
recon repair takes the majority's copy, so the lone acknowledged write is lost. With recon off (the default) the row is blocked.
Fix
A member holding the key refuses the insert as a conflict, the leader checks an INSERT as it checks an UPDATE, and a party that lost every member is vetoed. [party-lost] [party-cas]
Why severe
One row: two acknowledged inserts of one key, one node's copy different; the row is blocked, and a repair from the majority drops the lone acknowledged write.
Fixed - passed the matrix
