# YT Cluster 1.19.0

Published 2026-10-20. deb `yt-cluster` 1.19 (build 1.19.0), EL9 rpm 1.19.0. ytserv 1.2.0.

## Upgrade

- **Renamed from YaXAHA to YT Cluster:** package `yt-cluster` (deb and rpm; it conflicts
  with and replaces `yaxaha`), CLI `ytctl` (was `yxctl`), extension `yt_cluster` with GUCs
  `yt_cluster.auto_complete` and `yt_cluster.sync_delay_ms`, apt codename `yt-cluster`, docs
  in `/usr/share/doc/yt-cluster/`. The old `yaxaha` package is gone from the repository.
- The deb carries major.minor only (1.19): each build of a release replaces the one before
  under the same name. Install and update with `apt install --reinstall yt-cluster`. The
  rpm keeps the full version (1.19.0).
- `yt_config` is keyed by `(module, name)`. `ytctl --batch` migrates an existing table:
  duplicates keep the highest id, rows without a name are dropped.
- ytctl and ytserv must come from the same release for secret store admin calls.

## New: secrets and TLS

- **Secret store** (SKV), off by default (`skv_secrets`): a cluster master key made at
  genesis (`ytctl --skv-genesis`, with a recovery public key); secrets kept as encrypted X
  rows, opened on each node with its own P-256 node key. ytctl puts, gets, lists and removes
  secrets over the local unix socket only; `yt_info('X')` shows the store.
- Enrollment: members enroll their node key with the leader and get the master key wrapped
  for them once approved; a leader without the key enrolls itself and is wrapped by a holder.
- Master key rotation `ytctl --skv-rotate`: the new version is used once every member holds
  it, the old one stays valid for `skv_rotate_overlap_sec` (300) and is then retired.
  `--skv-retire` removes a node's keys and revokes it; `--skv-recover` restores with the
  recovery key.
- **Peer mTLS**, off by default (`peer_tls`): a cluster CA per master key version issues node
  certificates; TLS 1.3 on the same peer port, with revocation lists; a dial tries the
  newest certificate, then older ones; plaintext stays allowed until TLS is required.
- **Linked clusters over TLS:** the upper cluster's CA countersigns a lower cluster's CA after
  the lower az is approved, and the lower pins the upper's root (Z row `<az>.root`); a lower
  is admitted by its approved CA plus a one-use challenge; a lower CA rotation is signed
  again by continuity; neighbors cross-approve CAs. `ytctl --link-*` sets a relation up,
  `--ca-root` pins the cluster CA (`skv_ca_root`), `--skv-approve --fingerprint` checks the
  key.
- Approvals (node joins, cluster CAs, key enrollment) are plain SQL:
  `select yt_approve('<uuid>')`, or `ytctl --skv-approve`, which runs the same SQL. J rows
  hold non-secret data only and replicate; a new leader takes over pending and approved
  rows. An approved node that restarts comes back as Spare and is re-admitted by the proof
  of its approved key.
- Splits and combines carry the secret store: a split-off cluster gets its own store (values
  re-sealed, its leader runs genesis, the parent approves its CA); a combine carries values
  into the target, where the target's value wins.
- rppd Python functions read secrets with `SECRET.get`, `SECRET.get_bytes` and
  `SECRET.names`, for the names in the new `rppd_function.secret_names` column.

## New: data and operations

- **Parallel apply:** a table flag `parallel` (`ytctl --encode-table-cfg 'parallel'`, the TUI,
  `yt_info('a:')`) lets a receiver apply that table's subterms out of natural order on
  `parallel_apply_conns` lanes per database (default 4, 0 = off). Every table of the
  transaction and every direct foreign-key neighbor must carry the flag; a miss is redone in
  order. Counters in `yt_info('E')` `parallel_apply`.
- **Shard lease:** a node can lease a shard's subterms from the leader and check in that
  shard's writes itself; other writers get `[shard-lease] leased to <uuid> for <n>s` and ask
  the holder. Shown in `yt_info('E')` `hpc_lease`. A shard lease needs sequential consistency
  1 or more, a PK lease level 2. Unused subterms of an ended lease are rolled back.
- **Users databases:** one ytserv per PostgreSQL instance serves several databases. ytserv
  finds every database with the extension; C row `databases` (`*` auto, `-name` skip,
  `!name` detach, `name=schema.table` table override; a list without `*` is strict) and
  `db_reprobe_sec` (300). `yt_info('U')` lists them, `yt_info('U+')` probes again, and
  installing the extension calls it. Per-database overrides of `def_sql_timeout_sec`,
  `def_cluster_commit`, `clickhouse_db` and `sg_ignore`. A member that does not hold a
  table's database is left out of that table's party.
- Every setting has a scope (cluster, node, database, runtime); a setting written in the
  wrong scope is refused with a warning. Per-node rows `name@<node uuid>` win over the plain
  row, `log_level` included. View `yt_config_effective` and `yt_info('c')` show each
  setting's effective value and where it comes from.
- **Automatic recovery:** gaps left after the gap pull start a compare with the majority of
  holders and a repair under a recovery lock (the node leaves the table's party, its own
  writes get 40001). Rows that cannot be settled are blocked and released once every copy
  agrees. Settings `recovery_lock_ttl_sec` (300) and `recovery_auto_sec` (120), module `Y`
  rows, `yt_info('Y')`.
- **Client two-phase commit:** PREPARE TRANSACTION, COMMIT PREPARED and ROLLBACK PREPARED work
  on cluster-synced transactions. Needs `yt_cluster` in `shared_preload_libraries`: ytctl
  setup writes it into the extension's conf file, and uninstall removes the file.
- The extension sends the transaction's isolation level with its cluster commit.
- Merge: `merge_inc` (alias `inc_col`) increments only the listed columns; a text line
  changed on both sides is merged word by word; keyed and positional JSON array merge
  (`merge_key`). Overlapping changes are refused with 55409.
- Stale stream: a lagging node pulls whole terms over one streaming call (`stale_stream`,
  default 0, off; `stale_max_bytes`, default 1 MiB).
- Topology job `stage`: copies a table's existing rows from a source node, catches up and
  compares the copies; a stall is reported after 900 s (`stall_sec`).
- Table setting `ts_col`: recon suggests a time filter from it (`recon.suggest` rows).
- Event trigger `yt_ddl_end`: DDL on a synced table makes the schema gate check it again.
  `yt_setup` raises a NOTICE for a table without an integer primary key.
- A node stopping on a signal says bye to the cluster first. Terms roll after
  `term_ttl_hour` (default 24).
- **Usage meter:** a signed, chained ledger counts transactions per term, day, month and year,
  signed with a P-256 meter key. `yt_info('L')`, `L:ledger`, `L:report`; `ytctl --meter-key`
  and `--meter-report`. Linked clusters report to their upper. `meter_report_url` is empty
  by default: nothing is sent.
- **OpenTelemetry:** traces and metrics over OTLP gRPC (`otel_sample_ratio` 0.01,
  `otel_metrics_sec` 30, `otel_headers`); a `yt.tx` span per transaction carried to peers and
  into rppd (`TRACE` in Python); metrics yt.tx.duration, yt.peer.rtt, yt.queue.depth,
  yt.term, yt.leader, health gauges `yt.health.<metric>` and rppd.pp.*; OTLP logs
  (`otel_logs`, off by default); the trace id on CLUSTER DIVERGENCE and failed commit or
  apply lines.
- ClickHouse over TLS (an https URL, port 8443 by default) for the sink and the read path.
  The sink is insert-only with a bounded in-memory retry (`clickhouse_queue`, default 10000).
- `health_proactive_failover` (off by default): a leader whose disk or memory is critical or
  soon will be, or whose database is unreachable, hands leadership to its deputy.
- WAL cleanup (off by default): WAL files older than `fs_rm_after_cache_days` are removed at
  most once a day. Old complete WAL terms leave memory daily (`fs_cache_days`), and shutdown
  syncs every open WAL file.
- One rppd per database: setting `rppd_dbs` (ytctl `--rppd`); an instance starts once its
  database has a function and keeps its own queues; the leader is master of every instance.
- ytctl manages users databases (add; remove with detach), lints the config, and on purge
  drops the extension from every database; exit codes 33, 34 and 35. TUI: a Databases screen
  and a Config view with edit; the table editor gained `merge_inc`, `merge_key` and `ts_col`.

## Changed

- The join proof is possession of the node key plus its K row, and the master key when
  secrets are on; the app key is no longer part of it. `ytctl --skv-approve` refuses to sign
  when the `yt_join_gate` trigger is missing.
- A link (lower, upper or neighbor) is refused unless `skv_secrets` and `peer_tls` are on,
  and a split is refused without the secret store. With TLS required, only a lower split is
  allowed.
- The app key variable `SECRET` is removed from child processes, and ytserv is made
  non-dumpable when an app key is set.
- Settings `term_max_log` and `fs_max_transfer_size` removed. Merge option `outer=sign` /
  `ignore_sign` is refused; use `outer=consume`.
- Operator lines now at warn: rppd started or stopped per database, recon gap lines naming
  the missing subterms, a withdrawn lease.
- Dependency hardening after cargo audit: ytctl moved from rust-crypto to RustCrypto, ytserv
  dropped rsa for OpenSSL key types, YAML moved to serde-saphyr.

## Fixed

- Concurrent updates of one hot row could lose acknowledged increments when the party was
  the origin alone (`cluster_commit=nodes>=1`); the leader now serializes check-ins per row.
- An origin killed between `yt_complete(true)` and COMMIT on a fresh cluster could lose its
  transaction; its own unsettled records are now re-targeted or re-applied, not closed.
- After a crash PostgreSQL could reuse the xid of a transaction the cluster had reported
  committed. The extension flushes WAL before a cluster commit (one extra fsync per commit).
- A stop during the 2PC commit phase could leave a row on the party only; the origin now
  logs the commit in its WAL before COMMIT PREPARED, so its restart re-applies it.
- One delta could be applied twice on a node (a merge counter incremented twice) when a
  pull's copy ran beside the first apply. A cloned node pulled and replayed the subterms it
  was seeded with. A node could apply its own subterm again after the WAL cache was trimmed.
- The WAL cache could be trimmed past records a member still lacked; records are kept down to
  every member's reported position, and a write that would read past an unseen gap is
  refused with 40001. A WAL record still being written hid the missing subterm before it.
- An approved joining node was never admitted ("older than this leader remembers"), and a
  returning node never pulled the new term.
- A refusal from the leader counted as a vote, which could leave a phantom leader.
- A peer dial held locks while connecting: with one peer unreachable, party selection and
  `yt_info` stalled and check-ins failed with "Timeout expired". Pings and elections use
  their own connection per peer, so bulk traffic no longer gets a peer marked Down, and
  `yt_info` no longer waits behind other calls.
- A node a split moved out still counted in the old cluster's party, quorum and elections
  until the job ended. A split-off cluster whose store held only keys did not run genesis.
  An empty joiner could start its fill while the node restarted for a split switch.
  Combining clusters could fail to admit nodes.
- A joining copy that held the CA rows but not its own certificate could not start TLS.
  Turning TLS on could wait on the leader until the next store change.
- ytserv could hang at startup when `yt_ddl_end` fired on rppd's schema upgrade.
- An expired held lease blocked new leases forever. Parallel apply could run two copies of
  one in-flight subterm, and its counter counted every arrived subterm.
- The C row `def_cluster_commit` was never read, so tables fell back to half.
- `yt_ct_encode` / `yt_ct_decode` were stubs, so the `yt_tables_cfg` view was useless.
- COMMIT PREPARED in a fresh session missed the cluster when the library was loaded lazily.
- The transaction key map was never pruned and grew without bound.
- An empty joiner copies a table without an integer key by its whole primary key.
- ClickHouse sink posts time out after 30 s.
- A follower's per-database rppd could run an event locally before its config named a master.
- rppd's tables failed to deploy (42P10) under Schema Guard 1.10.

## Bundled

- Schema Guard Enterprise (sge, formerly rdbm) replaces rdbm: MIT licensed, no license key,
  built on Schema Guard 2.0.
- rppd 0.2.15 and 0.2.16: a circuit breaker per function per node (`breaker_fails`,
  `breaker_slow_ms`, `breaker_open_sec`, `breaker_open_max_sec`; failed events retried up to
  `max_attempts`, then to the `dlq` queue; state in `rppd_function_state`); an adaptive
  traffic shaper per function (`max_parallel`, `min_parallel`, `target_ms`, `rate_per_sec`,
  `burst`, `max_backlog`); tables upgraded at startup with Schema Guard; per-database
  instances. Fixed: an etcd queue message was acknowledged even when the function failed; the
  queue pick stopped at a busy line; cron jobs ran on every node, now on the rppd master
  only; events held while the breaker was open did not run after it closed.
- etcd (etcds 0.21): the AGPL dependency clap-serde-derive is gone; a config file is merged
  under explicitly given arguments (it used to be ignored); KV metrics `etcd.kv.ops` and
  `etcd.kv.duration`; no unsafe code. The secret mirror prefix stays local: remote callers
  cannot range, watch, snapshot or hash it, and clients cannot write it.
